01 · Comprendre les données

SQL — Compter sans perdre d’information.

SQL est un langage pour interroger une base de données relationnelle. Ici, la question est simple : combien d’incidents sont encore ouverts pour chaque service, y compris ceux qui n’en ont aucun ?

Commentaire du schéma

Lire ce visuel de haut en bas : d’abord les tables, ensuite la requête, enfin le tableau de résultat. La table services joue le rôle d’un catalogue ; la table incidents contient les événements rattachés à ce catalogue. Le point important est de garder visibles les services sans incident ouvert : un zéro apporte une information utile à la supervision.

1. Comprendre la relation entre les tables

Une table ressemble à une feuille structurée : chaque ligne décrit un élément et chaque colonne décrit une propriété. Dans services, id identifie un service et nom contient son nom. Dans incidents, service_id indique le service concerné.

PK signifie « clé primaire » : l’identifiant unique d’une ligne. FK signifie « clé étrangère » : une référence vers une ligne d’une autre table. La relation 1 → N se lit ainsi : un service peut être associé à plusieurs incidents. Le lien relie donc services.id à incidents.service_id.

2. Lire la requête étape par étape

SELECT s.nom, COUNT(i.id) AS ouverts
FROM services AS s
LEFT JOIN incidents AS i
  ON i.service_id = s.id
 AND i.statut = 'OUVERT'
GROUP BY s.id, s.nom
ORDER BY s.id;
  1. Partir des services. FROM services AS s choisit la table de départ. s et i sont des alias, des noms courts pour rendre la requête lisible.
  2. Associer les incidents ouverts. ON précise la correspondance entre les identifiants. La condition sur statut ne retient que les incidents ouverts parmi les lignes associées.
  3. Conserver tous les services. LEFT JOIN garde les lignes de la table de gauche, même sans incident correspondant. Déplacer le filtre de statut dans un WHERE peut éliminer ces services et changer le résultat.
  4. Compter par service. GROUP BY rassemble les lignes d’un même service ; COUNT(i.id) compte les identifiants non nuls. Le service sans correspondance obtient ainsi zéro. COUNT(*) compterait aussi la ligne conservée par la jointure.
  5. Stabiliser l’affichage. ORDER BY s.id, ajouté à la requête du schéma, fixe l’ordre des lignes. Sans cette clause, leur ordre n’est pas garanti.
Résultat attendu avec le jeu fictif ci-dessous
ServiceIncidents ouverts
DNS2
VPN1
API0

DNS aide à trouver l’adresse d’une machine à partir de son nom ; un VPN fournit une connexion réseau privée ; une API est un point d’échange avec une application. Le tableau mesure ici le nombre d’incidents déclarés ouverts, et non la disponibilité réelle de ces services.

Voir le petit jeu de données pour expérimenter

Exemple SQL minimal pour une base d’exercice vide. Il correspond uniquement au premier schéma : le modèle de l’API ajoute ensuite des champs comme le titre et la date de création.

CREATE TABLE services (
  id INTEGER PRIMARY KEY,
  nom VARCHAR(40) NOT NULL
);
CREATE TABLE incidents (
  id INTEGER PRIMARY KEY,
  service_id INTEGER NOT NULL REFERENCES services(id),
  statut VARCHAR(10) NOT NULL
    CHECK (statut IN ('OUVERT', 'FERME'))
);
INSERT INTO services VALUES (1, 'DNS'), (2, 'VPN'), (3, 'API');
INSERT INTO incidents VALUES
  (1, 1, 'OUVERT'), (2, 1, 'OUVERT'),
  (3, 2, 'OUVERT'), (4, 1, 'FERME'), (5, 2, 'FERME');
Le détail intermédiaire : l’index candidat

Un index sur (service_id, statut) peut aider certaines recherches. Comme un index de livre, il facilite l’accès à des informations ciblées, mais occupe de l’espace et doit être mis à jour. Il faut étudier le plan avec EXPLAIN et mesurer sur des données représentatives avant de conclure à un gain.

02 · Comprendre l’application

Spring Boot — Une demande, plusieurs responsabilités.

Java est le langage utilisé pour écrire l’application. Spring Boot facilite la mise en place de l’environnement Spring. Dans cet exemple, une API reçoit une demande de création d’incident et organise son traitement.

Commentaire du schéma

Les flèches montrent le parcours logique d’une demande, depuis son arrivée jusqu’à son enregistrement. Chaque bloc répond à une question différente : que reçoit-on, quelles règles appliquer et où conserver le résultat ? Cette séparation aide à localiser une erreur. Une demande mal remplie et une base inaccessible n’appellent pas le même diagnostic.

1. Ce que le client envoie

Un « client » peut être une interface web ou un outil de test HTTP. POST /api/incidents signifie ici « demander la création d’un incident ». Le corps de la requête utilise JSON, un format texte composé de noms de champs et de valeurs :

{
  "serviceId": 2,
  "titre": "VPN indisponible"
}

serviceId: 2 désigne le service VPN du jeu fictif. Le titre décrit le problème. Le client transmet ces informations ; c’est l’application qui décide si elles sont acceptables et comment les enregistrer.

2. Le rôle de chaque couche

  1. DTO — décrire les données entrantes. Un Data Transfer Object est une structure qui représente la demande. @NotNull exige un identifiant fourni ; @NotBlank refuse un titre nul, vide ou constitué uniquement d’espaces. Dans Spring MVC, @Valid sur le DTO reçu déclenche la validation configurée. Ces contraintes ne prouvent pas que le service existe.
  2. Controller — gérer l’échange HTTP. Le contrôleur reçoit la requête, transmet la demande au service métier et construit la réponse destinée au client.
  3. Service — appliquer les règles métier. Il vérifie que le service référencé existe, construit l’incident puis demande son enregistrement. Le cadre @Transactional délimite le traitement transactionnel : validation des écritures ou annulation selon les règles de rollback configurées.
  4. Repository — accéder aux données. Spring Data JPA fournit une interface d’accès aux entités Java persistées. Une méthode findByServiceId peut exprimer une recherche à partir du modèle de l’entité. Le retour List<Incident> permet de récupérer plusieurs incidents pour un service.
  5. PostgreSQL — conserver les enregistrements. La base stocke les lignes. La commande INSERT du schéma illustre l’écriture ; le SQL réellement émis dépend du mapping JPA et de sa configuration.

3. Comprendre les réponses

Choix de réponses HTTP dans cet exemple
CodeLecture pour le débutant
201La ressource « incident » a été créée.
400La demande est invalide, par exemple un titre vide.
404Le service référencé est introuvable, si cette réponse est configurée par l’application.

@RestControllerAdvice centralise la traduction des exceptions en réponses lisibles. Il faut définir les gestionnaires et les messages : ajouter l’annotation seule ne crée pas automatiquement toutes les réponses du tableau.

À retenir pour le support IT

Une erreur de validation se recherche d’abord dans les champs envoyés. Une erreur métier se recherche dans les règles de l’application. Un échec d’enregistrement demande aussi d’examiner les journaux et la connexion à la base. Le schéma sert à orienter la qualification de l’incident.

03 · Comprendre l’environnement

Docker Compose — Relier et faire durer.

Un conteneur exécute un logiciel à partir d’une image, qui regroupe son contenu et ses dépendances. Compose décrit comment plusieurs services doivent démarrer, communiquer et utiliser leur stockage.

Commentaire du schéma

Suivre d’abord les flèches du client vers l’API, puis de l’API vers la base. Le cadre app_net représente le réseau partagé par les conteneurs. Le cylindre pgdata représente le stockage conservé séparément. Ces trois éléments — accès, communication et persistance — expliquent l’essentiel du dessin.

1. Distinguer les deux chemins réseau

  1. Du client à l’API. Sur l’ordinateur qui exécute Docker, localhost:8080 vise le port 8080 de cet ordinateur. La publication 8080:8080 fait correspondre ce port de l’hôte au port 8080 du conteneur API.
  2. De l’API à la base. Les services api et db partagent le réseau app_net. L’API utilise le nom de service db et le port PostgreSQL 5432, plutôt qu’une adresse IP de conteneur susceptible de changer.
  3. Comprendre localhost. Dans le conteneur de l’API, localhost désigne ce conteneur, pas celui de PostgreSQL. C’est pourquoi la cible représentée est db:5432.

La base n’a pas besoin de publier un port sur l’hôte pour communiquer avec l’API sur leur réseau partagé. Cette configuration ne remplace pas les droits d’accès et l’authentification de la base.

2. Conserver les données

Le volume nommé pgdata est un espace géré par Docker, distinct de la couche d’écriture du conteneur. Si le conteneur de base est recréé en réutilisant ce volume, les données peuvent être retrouvées. Il faut configurer son montage au bon emplacement pour l’image PostgreSQL choisie.

Persistance ne signifie pas sauvegarde. Un volume peut lui aussi être supprimé ou endommagé. Il reste nécessaire de prévoir des copies et de tester leur restauration.

3. Attendre une base prête

Un conteneur démarré n’est pas forcément prêt à traiter des requêtes. Le healthcheck exécute un contrôle, par exemple pg_isready pour PostgreSQL. La dépendance condition: service_healthy indique à Compose d’attendre que ce contrôle réussisse avant de démarrer l’API.

Ce mécanisme organise le démarrage. L’application doit aussi gérer une perte de connexion ultérieure : il ne constitue pas, à lui seul, une solution de haute disponibilité.

4. Lire les commandes d’exploitation

docker compose up -d
docker compose ps
docker compose logs -f api
  • up -d crée ou met à jour les services définis dans le fichier Compose et les démarre en arrière-plan.
  • ps affiche leur état et les ports publiés.
  • logs -f api suit les journaux du service api au fil des nouveaux messages. Les journaux aident à comprendre ce qui échoue.

Ces commandes supposent Docker et Compose installés, un fichier de configuration dans le répertoire courant et une image API disponible ou constructible. Le schéma décrit l’organisation ; il ne fournit pas ces fichiers.

À retenir pour le diagnostic

Si l’API ne démarre pas, vérifier l’état de la base et ses journaux. Si elle démarre mais ne se connecte pas, contrôler le nom db, le réseau partagé, le port et les paramètres de connexion. Si les données disparaissent après recréation, examiner le volume monté.

Relier les trois schémas

Un incident VPN, de bout en bout.

  1. Un utilisateur signale « VPN indisponible ». Le client envoie une requête POST avec le service 2 et un titre.
  2. L’API Spring Boot vérifie la demande, contrôle le service référencé et prépare l’incident au statut OUVERT.
  3. Le repository demande l’écriture dans PostgreSQL. Dans l’architecture Docker, la connexion passe par db:5432 ; les données de la base sont conservées dans le volume monté.
  4. Après création réussie, une nouvelle interrogation SQL montre un incident VPN ouvert supplémentaire. Si l’on part du tableau initial, son compteur passe de 1 à 2.

Lien avec mon parcours NOC et support IT : comprendre ces dépendances aide à distinguer une anomalie de données, une erreur applicative et un problème d’infrastructure. Ce parcours d’étude complète les compétences de qualification, de lecture des logs et d’escalade.

Vérifier sa compréhension

Pourquoi garder API = 0 dans le tableau ? Pourquoi l’application utilise-t-elle db plutôt que localhost ? Et pourquoi conserver un volume ne suffit-il pas à protéger les données ?

Afficher les réponses

Le zéro confirme que le service figure dans le périmètre, même sans incident ouvert. Le nom db permet de joindre l’autre conteneur sur le réseau partagé, alors que localhost vise le conteneur courant. Enfin, un volume conserve les fichiers au-delà du cycle de vie d’un conteneur, mais une copie de sauvegarde indépendante et testée reste nécessaire.

Repères pour continuer

Quelques mots à garder en tête.

API
Interface qui permet à un logiciel de demander des données ou une action à un autre logiciel.
HTTP & JSON
HTTP organise l’échange requête/réponse ; JSON représente ici les données échangées sous forme de texte structuré.
Transaction
Ensemble d’opérations dont on contrôle la validation ou l’annulation pour préserver la cohérence des données.
Image & conteneur
L’image fournit le modèle logiciel ; le conteneur est son instance d’exécution.
Port
Numéro qui identifie un point d’accès réseau à un service sur une machine ou dans un conteneur.
Logs
Journaux produits par un logiciel : événements, informations et erreurs utiles au suivi et au diagnostic.
